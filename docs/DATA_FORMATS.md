# Retail Plus 5.2 data formats

This is the **import contract** for the rewrite. Each store's data is imported once at cutover ([DATA_LAYER_PLAN.md](DATA_LAYER_PLAN.md)), so the importer has to read these files exactly as described. Only the store-to-store exchange files would ever be written in this format, and only while some stores still run Retail Plus. The writing and locking rules below matter for that case only.

Sources: the files shipped inside `Retail52.exe`, and the data folder of the copy installed at `C:\Retail Plus 52` (installed and opened once on 2026-10-24, so most tables are still empty). Table structures were read from the file headers. Record contents were only inspected for the shipped sample inventory. Items marked **(to confirm)** still need checking against the original, using data from real use.

The table appendix at the end is generated by `tools/dbf/gen_schema_md.py`. Re-run it against a data folder from real use to pick up the tables that only appear once a feature is used.

## 1. Folder layout

| Path | Contents | Shared by |
|---|---|---|
| `<data root>\` (default `C:\Retail Plus 52`) | Company-wide tables: `CLIENTS`, `SUPPLIER`, `INVOICES`, `SETUP`, `USERS`, `NUMBERS`, `RMA`, `FASTKEYS`, `DEPT`, `CATEGORY`, `STAFF`, `PRNT`, plus `HEADER.TXT`, `FOOTER.TXT`, `POHEADER.TXT`, `V2.INI`, `PLUSFTP.INI` | All workstations (network share mapped to a drive letter) |
| `<data root>\<LOC>\` | One folder per location, named by the three-character location code (sample: `POS`, `TST`). Holds the inventory `<LOC>INV.DBF/.CDX/.FPT`, `BACKORD`, `POSTRANS`, `SUSPEND`, `RETADDR.ADD`, and one `SALESnnn.DBF` + `TOTALnnn.DBF` pair per POS station (`nnn` = station ID 001–999) | All workstations |
| `<data root>\<LOC>\PO\` | Purchase orders. Template `PO.DBF/.FPT`, and one order per file named `PO<number>.<LOC>`. The extension is the location code, not `.DBF`, and comes with `PO<number>.CDX` and `.FPT` | All workstations |
| `<data root>\PICS\` | Product and client photos. Records store absolute paths in `PICPATH` | All workstations |
| `<data root>\Reprint\` | Stored receipt output (last 500 transactions), plus optional PDF invoices. Format **(to confirm)** | All workstations |
| `C:\POS_SETTINGS\Plus50.INI` | Per-workstation settings: printers, ports, POS station ID, sort orders, card terminal, web shop, last opened files | One workstation |
| `C:\POS_SETTINGS\BACKUP\` | Automatic backup written on exit, when enabled | One workstation |

The manual (Appendix C) requires network workstations to reach the data through a mapped drive letter. UNC paths cause "Error 21". The rewrite should accept UNC paths, but it must store paths in the same form the original expects whenever it writes them into shared records (for example `PICPATH`).

## 2. File-level rules

- **DBF versions.** Tables without memos are dBASE III (`0x03`). Tables with memos are FoxPro 2.x with FPT (`0xF5`). Keep each table's version byte when rewriting it.
- **Code page.** Header byte 29 is `0x03` (Windows ANSI, code page 1252). Text, including memos, uses CP1252 with CRLF line endings.
- **Last-update date.** Bytes 1–3 hold YY/MM/DD, and VO 2.8 writes YY as a two-digit year (2026 → 26, 2011 → 11). Write it the same way. X# already does.
- **Structural CDX flag.** Header byte 28 bit 0 is set when the table has a production `.CDX` with the same base name. That index must be opened and kept up to date on every write.
- **Character fields longer than 255.** Clipper/VO convention: length = `len + dec × 256`. Example: `WEEKLY` is declared `C, len 88, dec 2`, which means C(600). A plain dBASE reader gets this wrong and misreads every field after it.
- **Numerics (N).** ASCII, right-aligned, with a fixed number of decimals (`"     30.00"`). Empty values are spaces.
- **Dates (D).** `YYYYMMDD`. An empty date is eight spaces.
- **Logicals (L).** `T` / `F`. Some tables store logicals as text in C fields instead (`FASTKEYS`: `"TRUE "` / `"FALSE"`).
- **Memo (FPT).** Big-endian block header with type (1 = text) and length. Block size is 64 in new files and 32 in some older ones. Use whatever the file header says.
- **Deletion.** Records are soft-deleted (`*` in byte 0) and only physically removed by Rebuild, or on program exit for some tables. Every read must skip deleted records. "Undelete Items" depends on this.
- **Older structures.** Tables written by older versions can lack fields. For example `TSTINV.DBF` has no `SCALE`, `WEBDELETE`, `THCWEIGHT`, `SUPPCODE` or `BRAND`. The original's Rebuild command upgrades them. The rewrite must read missing fields as blank and only add them during Rebuild.
- **Unknown fields.** If a table has fields the rewrite doesn't know about, preserve them unchanged on write.

## 3. Index tags

Tag names and key expressions must match exactly, because the original selects orders by tag name. The tag named after the table (for example `POSINV`, `CLIENTS`, `PO1001`) changes with the file name. For the inventory it is `<LOC>INV`.

| Index | Tag → key expression |
|---|---|
| `<LOC>INV.CDX` | `DEPT` → `UPPER(DEPT)+UPPER(PLU)`; `PLU` → `UPPER(PLU)`; `<LOC>INV` → `UPPER(PROD)`; `SUPPCODE` → `UPPER(SUPPCODE)`; `SUPPLIER` → `UPPER(SUPPLIER)+UPPER(PLU)`; `YTDTOTAL` → `YTDTOTAL` |
| `CLIENTS.CDX` | `ACCTNO` → `Upper(ACCTNO)`; `CLIENTS` → `UPPER(LNAME)`; `CLIENTTYPE` → `Upper(CLIENTTYPE)`; `COMPANY` → `UPPER(COMPANY)`; `CUSTNO` → `UPPER(CUSTNO)`; `EMAIL` → `upper(EMAIL)`; `LASTPURCHA` → `DESCEND(LPURCHASE)`; `STATE` → `UPPER(STATE+CITY)`; `WORKPHONE` → `WORKPHONE`; `ZIP` → `UPPER(ZIP)` |
| `SUPPLIER.CDX` | Same as `CLIENTS.CDX`, except the `UPPER(LNAME)` tag is named `SUPPLIER` |
| `INVOICES.CDX` | `ACCTNO` → `ACCTNO`; `COMPANY` → `UPPER(COMPANY)`; `INVOICES` → `Upper(LNAME)`; `INV_DATE` → `DESCEND(INV_DATE)`; `INV_NO` → `INV_NO` |
| `BACKORD.CDX` | `COMPANY` → `UPPER(COMPANY)`; `ORDATE` → `ORDATE`; `PROD` → `PROD` |
| `USERS.CDX` | `USERS` → `USERNAM` |
| `PO<n>.CDX` | `DEPT` → `UPPER(DEPT)+UPPER(PLU)`; `PLU` → `UPPER(PLU)`; `PO<n>` → `UPPER(PROD)`; `REORDERNO` → `REORDERNO`; `SUPPLIER` → `UPPER(SUPPLIER)+UPPER(PLU)` |

None of the tags have FOR conditions, and all are ascending. Descending order is done with `DESCEND()` in the expression.

Key encoding, confirmed on VO-written files (see [the Phase 0 spike](spikes/phase0-rdd-spike.md)):

- Character keys are padded with spaces and compared byte by byte (ordinal).
- Numeric and date keys use the FoxPro encoding: big-endian IEEE double with the sign bit flipped, or all bits inverted for negatives. A date is its Julian day number.
- `DESCEND(date)` = 5231808 − Julian day. An empty date gives 5231808.

## 3a. Locking

Record locks are 1 byte at `0x80000000 + recno`, the append/header lock is 1 byte at `0x80000000`, and a file lock covers `0x80000001`–`0xFFFFFFFF`. Index updates lock `0xFFFEFFFF`–`0xFFFFFFFF` exclusively; index reads take one random shared byte in `0xFFFF0000`–`0xFFFFFFFF` (Comix scheme). This is what the X# runtime does in ANSI mode, which X# says matches VO. It was never confirmed against `Plus50.exe`. With a one-time import it no longer matters: the importer reads copies of the files while Retail Plus is closed.

## 4. Packed text inside fields and memos

The original stores lists as delimited text. These encodings need round-trip tests: reading a value and writing it back must give identical bytes.

## 5. Settings

- **`SETUP.DBF`** (one record, shared by all workstations): business ID and address, two taxes with names and rates, tax inclusive/exclusive (`VAT`), compound tax (`TAXCOMP`), interest rate and grace period, bonus points (`DP_*`), security switches (`STAFF_ID`, `VOID_ID`, `STAFFDISC`), UK date format, random-weight barcodes (`UPCWEIGHT`), auto save (`YNSAVESALE`), gift card maximum, forced RMA, cash discount, THC limit, credit card surcharge (`CCARDCHRG`). Full field list in the appendix. In the installed copy `CCARDCHRG` (N 3,2) holds `***`, a numeric overflow, so readers must treat unreadable numerics as blank rather than fail.
- **`NUMBERS.DBF`** (one record): the last invoice, customer, PO and RMA numbers used (the sample has `LAST_PO` = 1001 with `PO1001.POS` present), so numbering continues at the value + 1. Each increment must happen under a record lock so two workstations never take the same number.
- **`C:\POS_SETTINGS\Plus50.INI`** (per workstation). Sections `[STARTUP]`, `[INVENTORY]`, `[CLIENTS]`, `[INVOICES]`, `[PO]`, `[POS]`, `[MERCURY]`. `[POS]` holds about 60 keys for printers, cash drawer, pole display, scale, fast scan, auto save, card processing (ICVerify, X-Charge, MPS, Mercury, Global), web shop and email client. The key names are in the installed file. This document deliberately doesn't copy their values.
- **`V2.INI`** in the data root holds the demo session counter. The rewrite has no reason to touch it.
- **`USERS.DBF`**: `USERNAM`, `P_WORD` C(10), access level `PRV` (0–4; 0 = trainee), `PWCHANGE`. How the password is stored (plain or encoded) is **(to confirm)**. The importer either hashes it, if it turns out to be plain text, or makes each user set a new password at first login ([DATA_LAYER_PLAN.md](DATA_LAYER_PLAN.md), open question 3).

## 6. Printer and report files

- **Label templates (`*.lbl`)** are text files in the printer's own language, with `<<FIELD>>` placeholders (`<<DESCRIPTION>>`, `<<SIZE>>`, `<<PRICE>>`, `<<ITEMLOOKUPCODE>>`). Zebra templates are EPL2, Wasp templates are TSPL, and the Cognitive Advantage LX template is CPL. Users edit them, so the rewrite should load and fill the same files rather than replace them.
- **Report layouts (`*.RPT`)** are ReportPro 2 binary files (signature `RPW_V02.001_RPT_FILE`). The rewrite rebuilds each report in its own engine, using the RPT list as the inventory of reports to recreate.
- **`PRNT.DBF`** (`LINE` C(160)) is a line buffer used to stage text reports.
